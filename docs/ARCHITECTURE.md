## 0. 왜 새로 만드나

팀 코드를 안 쓰는 이유는 품질 문제가 아니다. 오히려 잘 돼 있다. 다른 목적을 위해서다.

| 목적 | 팀 프로젝트 | 새 프로젝트 |
|---|---|---|
| 소유 | 공동 | **본인** |
| 설명 책임 | 분담 | **전부 본인** (대학원 면접·포트폴리오) |
| 범위 | 팀 일정에 묶임 | **본인이 정함** |
| DDA | 기능 중 하나 | **중심** |

→ **"내가 전부 설명할 수 있는 코드"**가 제1 목표. 이게 아키텍처 결정의 기준이다.

## 3. 보스 5종이 아키텍처에 주는 영향 ← v1에서 가장 크게 바뀐 부분

**2종이면 단순한 패턴 실행기로 충분하다. 5종이면 아니다.**
각 보스가 요구하는 시스템이 전혀 다르고, **나중에 끼워 넣을 수 없는 것들**이 섞여 있다.

| 보스 | 이 보스 때문에 필요한 것 |
|---|---|
| 아라쿠스 | 근접 히트박스 · 투사체(방패) · 돌진 + **충돌 오브젝트로 저지** |
| 파네스 | **탄막**(유도·부채꼴·반사) · **복층 공중 발판** · 결계벽 파괴(DPS 체크) · **분신 식별 퍼즐** |
| 아디쿠스 | **소환물 AI**(죄수·망자) · 사슬 포획(플레이어 끌어오기) · 반사막 · 저울 기믹(**무게 집계**) |
| 에텔로스 | **무기 생성 5종** · 맵 전역 기둥 패턴 · **보스가 플레이어를 패링** · 디버프 부여 |
| 카로스 | **패턴 복제·재생**(환영/환각/잔상) · 안전지대 기믹 · **플레이어 키 봉인** |

### 3.1 이 때문에 추상화 레벨을 올린다

```
PatternExecutor (추상)
├─ MeleeExecutor       근접 히트박스
├─ ProjectileExecutor  투사체 (유도 / 직선 / 부채꼴 / 반사)
├─ DashExecutor        돌진 (저지 가능 여부 포함)
├─ SummonExecutor      소환물 (죄수 · 망자 · 분신)
├─ AreaExecutor        장판 · 기둥 · 레이저 · 안전지대
└─ ReplayExecutor      다른 패턴을 그대로 다시 실행 ← 카로스 전용
```

`ReplayExecutor`가 특히 중요하다. 카로스의 환영·환각·잔상은
**"이미 실행한 패턴을 지연·복제해서 다시 트는 것"**이다.
패턴 실행이 *재생 가능한 데이터*로 설계돼 있지 않으면 **나중에 못 만든다.**

### 3.2 플레이어 제약 인터페이스

```csharp
public interface IPlayerConstraint
{
    bool DashBlocked { get; }     // 카로스: 회피 키 봉인
    bool AttackBlocked { get; }   // 침묵 디버프
    float DamageDealtMul { get; } // 에텔로스: 빛 피격 → 공격력 감소
}
```

**보스가 플레이어 능력을 건드리는 설계**(카로스 회피 봉인, 에텔로스 디버프)가
기획에 이미 들어 있다. 플레이어가 외부 제약을 받아들일 창구를 처음부터 둔다.

### 3.3 아레나를 데이터로

파네스는 **복층 공중 발판**이, 아라쿠스는 **충돌 오브젝트**가, 카로스는 **사슬 배치**가 필요하다.
아레나를 씬에 손으로 박지 않고 `ArenaDefinition`(SO)으로 둔다.

### 3.4 솔직한 비용

- **구현 기간이 2종의 3~4배**가 된다 (2.5배가 아니다 — 파네스·카로스가 새 시스템을 많이 요구한다)
- 보스 3종(파네스·에텔로스·카로스)은 **타임라인 수치가 아직 이미지 안에만** 있다. 추출 작업이 선행돼야 한다
- 단계 0~2(뼈대·플레이어)가 **느려진다.** 5종을 받을 추상화를 처음부터 깔아야 하므로

→ 그래도 가기로 한 결정이다. 대신 **구현 순서로 리스크를 관리**한다 (§7).

## 4. 코드 구조

### 4.1 입력을 인터페이스로 분리 `[확정]`

```csharp
public interface IPlayerInput
{
    float Horizontal { get; }
    bool JumpHeld { get; }
    bool JumpPressed { get; }
    bool DashPressed { get; }
    bool ParryPressed { get; }
    bool AttackPressed { get; }
    bool SkillQPressed { get; }
    // …
}
```

| 구현체 | 용도 |
|---|---|
| `KeyboardInput` | 사람이 플레이 |
| `ReplayInput` | 기록된 입력 재생 (버그 재현) |
| `AgentInput` | **페르소나 에이전트가 플레이** |

**왜**: DDA 웜 스타트에 사람 12명 × 10전이 필요한데 그게 일정 병목이다.
입력이 인터페이스면 초보/중수/고수 에이전트가 수천 판을 돌린다.
DDA 설계서 12장의 가상 시뮬레이션을 **실제 게임 위에서** 돌리는 셈이고,
"학부 규모에서 DDA를 학습시키는 데이터 효율" 이라는 논문 빈칸을 정면으로 노린다.

> 비용은 처음에 안 쓰면 0이다. 나중에 바꾸려면 전부 뒤져야 한다.

### 4.2 어셈블리로 의존 방향 강제

```
RT.Core        무엇도 참조하지 않음 (이벤트 · 인터페이스 · 수학)
RT.Data        ← Core                (ScriptableObject 정의)
RT.Player      ← Core, Data
RT.Boss        ← Core, Data
RT.Telemetry   ← Core, Data           (기록만)
RT.Backend     ← Core, Data, Telemetry (서버 · DB)
RT.DDA         ← Core, Data, Telemetry
RT.UI          ← Core, Data
RT.Game        ← 전부                  (조립만)
```

지키는 규칙 세 개:

1. **`RT.DDA`는 `RT.Boss` · `RT.Player`를 참조하지 않는다.**
   DDA는 "패턴 ID → 보정 단계"만 내놓고, 주입은 `RT.Game`이 한다.
   → DDA를 빼도 게임이 돈다 = **대조군 빌드가 공짜**
2. **`RT.DDA`의 학습 코어는 Unity를 참조하지 않는 순수 C#.**
   → EditMode 테스트 가능, `ddasim` 파이썬과 같은 입력에 같은 출력인지 대조 가능
3. **`RT.Backend`가 끊겨도 게임이 돈다.** 로컬 CSV로 폴백.

### 4.3 플레이어는 상태 기계

```
RT.Player/
├─ PlayerContext.cs       공유 상태 (체력 · 게이지 · 대시 스택 · 제약)
├─ PlayerStateMachine.cs
├─ States/                Idle · Move · Jump · Fall · Dash · Attack
│                         · Skill · Parry · Hit · Stun · Dead
└─ PlayerStats.cs         (SO) 모든 수치
```

한 파일 **300줄**을 넘기지 않는다.

### 4.4 궁극기 계수 체계 수정

`SPEC.md` §13-K. 기존 규칙(원본 계수의 75%)이면 계승 궁극기가 **콤보 2타와 같은 피해**다.
→ 총 계수를 직접 지정. 기본 1000% / 계승 1400%. (보스 HP 확정 후 재계산)

## 5. 서버 · 데이터베이스 `[확정 — 필수]`

### 5.1 무엇을 저장해야 하나

| 종류 | 내용 | 특징 |
|---|---|---|
| **세이브** | 성장 수치 · 보유 궁극기 · 보스 처치 상태 · **DDA 모델(A 324개 + b 18개)** | 플레이어별. 읽기/쓰기 |
| **연구 기록** | `BattleSummary` · `PatternStats` (패턴별 피격·패링·회피·단계·문맥·예측) | **쓰기 많음. 전체 집계 필요** |
| **실험 배정** | `experimentGroup` (dda / control) | 계정 생성 시 1회 |

연구 기록이 까다롭다. 여러 플레이어 기록을 **한꺼번에 읽어 집계**해야 한다 —
웜 스타트 초기값을 만들고, 두 그룹을 Mann-Whitney U로 비교해야 하므로.

### 5.2 후보

| 안 | 구성 | 장점 | 단점 |
|---|---|---|---|
| **A. UGS 전부** | Authentication + Cloud Save + Analytics | 유니티 공식, 통합 쉬움. 팀 설계서 원안 | **Analytics raw 데이터 추출이 제한적** — 연구 분석에 불리 |
| **B. Supabase 전부** | 익명 인증 + Postgres | **SQL로 바로 집계**, 무료 500MB, 분석에 최적 | Unity 공식 SDK 없음 (REST로 붙임) |
| **C. 하이브리드** | UGS Auth + Cloud Save / Supabase에 연구 기록 | 각자 잘하는 것 | 연동 지점이 둘 |

**→ B (Supabase 전부) 확정 `[2026-10-23]`**

이 프로젝트에서 서버의 존재 이유 8할이 **연구 데이터 집계**인데, 거기서 A가 가장 약하다.
SQL 한 줄로 `SELECT ... GROUP BY pattern_id, dda_step` 이 되는 게 결정적이다.

**Supabase가 뭔가**: Postgres 데이터베이스 + 인증 + REST API를 묶어 무료로 주는 서비스다.
서버를 직접 띄우지 않아도 되고, 웹 대시보드에서 SQL을 바로 칠 수 있다.

| 항목 | 내용 |
|---|---|
| 무료 티어 | DB 500MB · 월 50,000 활성 사용자 |
| 이 프로젝트 예상 사용량 | 전투 기록 수천 건 ≈ 수십 MB. **무료로 충분** |
| 서정범이 할 일 | 가입 → 프로젝트 1개 생성 → **Project URL + anon key** 전달 |
| 내가 할 일 | 테이블 스키마(SQL) 작성 · Unity REST 클라이언트 · 재전송 큐 |
| 주의 | 무료 프로젝트는 **1주일 비활동 시 일시정지**된다 (버튼 한 번으로 복구) |

### 5.3 어느 쪽이든 지키는 것

- **오프라인에서 게임이 끝까지 돌아간다.** 서버는 거들 뿐
- DDA 학습은 **로컬에서** 한다 (DDA 설계서 8.2: "학습 주체 = 플레이어 PC")
- 서버 실패 시 로컬 CSV에 쌓고 나중에 올린다 (전시장 대비)
- `RT.Backend`를 통째로 꺼도 컴파일이 된다

## 6. 아트 — 내가 할 수 있는 것과 없는 것

### 내가 코드로 만들 수 있는 것

| 항목 | 방법 |
|---|---|
| 플레이스홀더 캐릭터·보스 | 기하학적 실루엣 (박스/원/다각형) — `Texture2D` 생성 또는 SVG |
| **공격 궤적 이펙트** | 파티클 + 셰이더 (베기 반달, 충격파, 먼지) — 꽤 그럴듯하게 나온다 |
| **패링 신호 번쩍임** | 셰이더 (플래시·아웃라인) — 게임플레이에 직결되므로 우선순위 높음 |
| 투사체·장판·레이저 | 파티클 + 프로시저럴 메시 |
| **UI 전체** | 체력바·게이지·쿨다운·디버그 패널 — 코드로 충분히 좋게 나온다 |
| 타일맵 · 아레나 | 단색 블록 + 라이팅 |

### 이미지 생성 AI로 되는 것 / 안 되는 것 (2026-10 기준)

**나(이 세션)는 이미지 생성 도구가 없다.** 아래는 별도 AI 도구를 썼을 때의 이야기다.

| | 상태 | 비고 |
|---|---|---|
| 단일 스프라이트 (캐릭터·적·아이템 1장) | ✅ **잘 된다** | 보스 5종 정지 이미지는 뽑을 만하다 |
| 배경 · 패럴랙스 레이어 | ✅ 잘 된다 | 타일링·애니메이션이 필요 없어서 |
| UI 아이콘 | 🔶 보정 필요 | 픽셀 정렬이 안 맞아 다듬어야 한다 |
| 컨셉 아트 · 스타일 탐색 | ✅ 잘 된다 | 기획서의 '애니메이션 참고 포즈' 칸을 채우기 좋다 |
| **애니메이션 프레임** | ❌ **약하다** | 프레임마다 디테일이 흘러간다. 걷기 모션에서 벨트 버클 위치가 계속 바뀌는 식 |
| **타일셋** | ❌ **제일 약하다** | 모델이 16×16 그리드 개념이 없어 이음매가 생긴다 |

> 정리하면 — **AI는 캐릭터를 *디자인하는* 아티스트지, *움직이는* 애니메이터가 아니다.**

**이 프로젝트에 주는 의미**가 중요하다.
보스 5종 × 패턴 8~20개이고, 패턴마다 **선딜·판정·후딜 모션**이 필요하다.
정지 이미지는 AI로 되지만 **그 모션은 안 나온다.** 여기가 진짜 병목이다.

### 그래서 현실적인 선택지 셋

| 안 | 방법 | 평가 |
|---|---|---|
| A. 에셋 팩 | 에셋스토어·itch.io에서 **애니메이션이 딸린** 캐릭터를 가져온다 | 가장 빠르다. 보스 5종이 다 맞는 팩을 찾기는 어렵다 |
| **B. AI 이미지 + 2D 리깅** | AI로 보스 정지 이미지 → 부위별로 자르기 → Spine·DragonBones·Unity 2D Animation으로 리깅 | **프레임 일관성 문제를 우회한다.** 리깅 학습 비용이 있다 |
| C. 플레이스홀더 유지 | 기하학적 실루엣으로 끝까지 | 비용 0. 포트폴리오로는 약하다 |

**추천: 단계 0~6은 C, 그 뒤에 B.**
2D 액션의 손맛은 애니메이션 품질보다 **판정·히트스톱·이펙트**가 좌우한다.
그 셋은 내가 코드로 만들 수 있으므로, 플레이스홀더로도 "재미있는지"는 판정된다.
그리고 **DDA 실험에는 아트가 아예 필요 없다.**

| 항목 | 조달처 |
|---|---|
| BGM · SFX | freesound.org · 에셋스토어 (AI 음악 생성도 선택지) |

## 7. 구현 순서 (5종 반영)

단계마다 **플레이 가능한 상태**로 끝낸다.

| 단계 | 내용 | 끝났을 때 |
|---|---|---|
| 0 | 프로젝트 뼈대 · 어셈블리 · 입력 인터페이스 | 에러 0으로 열린다 |
| 1 | 플레이어 기동 (이동·점프·대시·코요테·버퍼) | 박스로 손맛을 본다 |
| 2 | 전투 (콤보·Q/W/E·패링·피격·히트스톱) | 허수아비를 때리고 패링한다 |
| 3 | **보스 프레임워크** (PatternExecutor 6종 + 아레나) | 더미 보스가 전 유형 패턴을 쓴다 |
| 4 | **아라쿠스** | 1층이 클리어된다 |
| 5 | 텔레메트리 + **서버·DB** | 기록이 DB에 쌓인다 |
| 6 | **DDA** (규칙 기반 → LinUCB) | 단계가 전투마다 바뀐다 |
| 7 | 로비 · 성장 · 궁극기 계승 | 루프가 닫힌다 |
| 8 | **아디쿠스** (소환물·기믹) | 계승 궁극기를 2층에서 쓴다 |
| 9 | **파네스** (탄막·복층 발판) | — |
| 10 | **에텔로스** (무기생성·보스 패링) | — |
| 11 | **카로스** (패턴 복제·키 봉인) | — |

> **3단계를 보스 하나보다 먼저 두는 이유**: 5종을 받을 실행기를 먼저 세워야
> 보스를 추가할 때마다 프레임워크를 뜯는 일이 안 생긴다.
>
> **6단계까지 끝나면 논문 실험이 가능하다.** 보스 9~11은 게임 완성도용이다.
> 일정이 밀리면 여기서 자른다.

## 8. 지키기로 하는 규칙

1. 한 파일 **300줄**을 넘기지 않는다 — 이유는 §8.1
2. 매직 넘버 금지 — 수치는 ScriptableObject
3. `Input.GetKey`를 플레이어 로직에서 직접 쓰지 않는다
4. `RT.DDA`는 게임플레이 어셈블리를 참조하지 않는다
5. `RT.Backend`가 꺼져도 게임이 끝까지 돌아간다
6. DDA 학습 코어는 Unity 없이 테스트된다
7. 새 시스템은 **EditMode 테스트 또는 디버그 화면**을 같이 만든다

### 8.1 왜 300줄인가

**팀 코드의 `PlayerMovement.cs` 2614줄이 반면교사다.** 그 파일 때문에 실제로 벌어진 일:

- README에 *"정훈의 파일이라 합의 먼저가 맞다고 보고 손대지 않았습니다"* 라고 적히고, **아무도 못 건드리는 영역**이 됐다
- 기획서가 요구한 "패링 가능/불가 구분"이 **두 줄이면 되는데도** 그 파일 안에 있다는 이유로 미뤄졌다
- 어제 내가 고칠 때도 전체를 못 읽고 `grep`으로 더듬었다

이 프로젝트의 제1 목표가 **"내가 전부 설명할 수 있는 코드"** 인데,
면접에서 2614줄짜리 클래스를 설명할 수 있는 사람은 없다.

그리고 **AI와 같이 작업할 때 특히 중요하다.**
파일이 크면 내가 전체를 읽는 비용이 커지고, 일부만 보고 고치면 실수 확률이 올라간다.
작은 파일은 통째로 읽고 통째로 바꿀 수 있다.

> **솔직히 300은 임의의 숫자다.** 250이든 400이든 상관없다.
> 요지는 "한 파일에 한 가지 책임"이고, 300줄은 그걸 알려 주는 **신호등**이다.
> 넘으면 "쪼갤까?"를 한 번 생각하는 트리거로 쓴다. 억지로 쪼개면 오히려 흐름 추적이 어려워진다.

### 9.1 "타임라인 추출"이 무슨 뜻인가

보스 기획서 PDF의 패턴 타임라인이 **손으로 그린 이미지**다. 텍스트로 안 읽힌다.

어제 아라쿠스는 PDF 페이지를 이미지로 렌더링해 눈으로 읽어 냈다.
그래서 `일반 공격 1 = 0s → Hit 1.05s → 2.1s` 같은 실측값이 나왔다.

**파네스 · 에텔로스 · 카로스는 아직 안 했다.** 보스당 10~15장을 읽어야 한다.

→ **그 보스를 구현하기 직전에 한다.** 지금 다 뽑아도 몇 주 뒤에나 쓰고,
그 사이 설계가 바뀌면 다시 해야 한다. 지금 몰아서 하면 진도가 멈춘다.
